# /lite:plan

负责把自然语言需求整理为可执行上下文，并按当前模式输出：默认模式生成 `lite-spec` 的计划与任务；外部规划体系模式写入项目既有规划体系；直做模式确认阻塞分歧后直接实现。同时会顺带判断这次需求是否产出可长期沉淀的知识。

## 适用场景

- 用户显式提到 `lite-spec`、`$lite-spec` 或 `/lite:plan`，并希望按该工作流梳理上下文、访问资料、确认分歧或整理计划推进当前需求
- 用户说“先帮我整理需求，不要改代码”
- 用户给出模块路径、需求说明、资料链接、数据库变更说明、运行手册或外部文档，希望先出计划
- 需求进入实现前，需要先整理上下文、识别风险，并在需要时生成对应模式的任务产物
- 默认模式下，希望把单次需求整理为项目内 `plans/YYYY-MM-DD-<slug>/`
- 希望在整理需求时同步发现“这次有没有长期知识值得沉淀”，避免实现完成后遗漏沉淀

## 默认流程

1. 接收自然语言需求
2. 提取 repo、模块/服务、功能目标及相关资料
3. 若用户明确要求“直接实现”“直接改代码”“不要生成计划/任务”等，进入直做模式：保留 `/lite:plan` 的上下文梳理、资料访问、风险识别和澄清能力，但当前请求不进入计划产物流程；不要生成 `plan.md`、`tasks.md`，也不要创建 `plans/` 工作区；完成阻塞性分歧确认后直接改代码
4. 先检查目标仓库是否已经明确采用 `OpenSpec`、`Superpowers` 或其他稳定规划框架
5. 若已命中其他规划框架，则进入外部规划体系模式：保留 `/lite:plan` 的上下文梳理、资料访问、风险识别和澄清能力，但不要生成 `lite-spec` 的 `plan.md`、`tasks.md`，也不要创建 `plans/` 工作区；最终计划、任务或变更说明应写入项目原有规划体系的主真源，并遵循其模板、命名和状态流转
6. 判断是否需要切到 `/lite:d2c`；若是设计稿直做场景，先读取 `references/d2c/index.md` 判断是否转入该入口
7. 由 `/lite:open` 检查访问方式与凭证；若缺失则停止
8. 判断是否存在关键歧义；若存在则先读取 `references/plan/clarification.md` 并提出高价值澄清问题
   - 默认一次提出 1 到 3 个高价值问题；若阻塞性歧义较多，可扩展到 4 到 5 个，并按优先级排序；若超过 5 个，则分批确认
   - 非直做模式下，若待确认项总数只有 1 到 2 个，则无论优先级高低，都必须先逐项提问确认；确认前禁止生成最终计划 / 任务产物或进入 `Plan Ready`
   - 直做模式下，不要求确认所有低优先级分歧；只有影响实现方向、模块/服务落点、接口契约、数据结构、交互主流程、验收标准或会导致明显返工的分歧才阻塞落代码
   - 直做模式下，对不影响实现方向的低优先级细节，优先按项目已有惯例和相邻实现自行决策，并在最终说明中标注关键假设
   - 提问前先明确告知用户“还有几个问题需要确认，确认后我会继续下一步”
   - 若当前运行环境提供结构化选项输入能力，优先使用带选项的交互方式
   - 若无法使用结构化选项输入，则直接改用自然语言文本提问，不向用户解释工具或环境限制
9. 当高优先级歧义已解决、或明确可降级为非阻塞项，且非直做模式下“仅有的 1 到 2 个待确认项”也已完成逐项确认后，根据当前模式输出：默认模式生成项目内 `plan.md`、`tasks.md`；外部规划体系模式写入原规划体系的主真源；直做模式不生成计划文件，改为直接实现
10. 判断当前需求是否产出可长期沉淀的知识；若有，则先按 `references/knowledge/rules.md` 判断是否值得沉淀，再结合 `references/shared/layout.md` 给出长期主真源落点与沉淀建议
11. 非直做模式下，引导用户审核已生成文件；用户明确批准前不进入代码实现，也不继续按计划自动修改用户代码。直做模式下，完成实现后说明关键默认决策、假设与验证结果。

## 产物目录

```text
<repo>/plans/YYYY-MM-DD-<english-slug>/
  plan.md
  tasks.md
```

说明：

- `plan.md` 为实施计划
- `tasks.md` 为待审核任务清单
- 仅默认模式使用上述目录；外部规划体系模式使用项目原有规划体系的目录、文件名、模板和状态流转
- 直做模式不创建上述目录，也不生成计划或任务文件

## 输出要求

- 如果用户输入包含外部资料 URL，且该资料按规则属于需要登录或可能需要凭证的来源，则先完成 `/lite:open` 检查
- 在 `/lite:open` 未确认“资料可访问”前，不生成 `plan.md`、`tasks.md`
- 若直接访问页面 URL 仅返回登录页、站点壳页面或无法取得目标资料正文，先回到 `/lite:open` 继续做凭证与机器接口二次验证；只有在 `show-credentials` 无凭证，或机器可判定目标仍返回未登录 / 无权限 / 非预期结果时，才按“凭证缺失或失效”处理，不得降级为普通待确认项继续产出最终 task
- 当 `references/plan/clarification.md` 所定义的高优先级歧义仍未明确时，必须先提问，禁止生成 `Plan Ready` 状态的 `plan.md` / `tasks.md`
- 非直做模式下，当待确认项总数只有 1 到 2 个时，无论其原本属于高优先级还是低优先级，都必须先提问确认，禁止直接生成 `Plan Ready` 状态的 `plan.md` / `tasks.md`
- 若已经识别到阻塞性澄清问题，则当前回合应停在澄清状态，而不是一边提问一边生成产物或落代码
- 若澄清问题原本适合用选项式交互但当前未采用该方式，仍要让用户清楚知道这只是“确认若干问题后继续下一步”的中间步骤，不要让用户误以为流程已中止
- 直做模式下，只有阻塞性分歧必须确认完才能落代码；不要因为少量低优先级文案、提示方式、样式微调等非阻塞问题而暂停实现
- 默认模式下，生成 `plan.md`、`tasks.md` 后默认立即停止在审查阶段，不继续进入实现、改代码、执行任务清单或补做未获批准的计划步骤
- 外部规划体系模式下，不生成 `lite-spec` 的 `plan.md`、`tasks.md`；完成资料访问、上下文梳理和必要确认后，按项目原有规划体系生成或更新对应文档，并停在该体系规定的审查阶段
- 若用户只是泛泛说“帮我实现”“帮我改页面”“加功能”，通常仍先生成计划并停在审查阶段；但若用户明确说“直接实现”“直接改代码”“不要生成计划/任务”等，则进入直做模式：继续按需访问原型图、Figma、接口文档等资料，遇到关键分歧或阻塞问题先确认，不生成 `plan.md`、`tasks.md`，确认后直接按用户目标实现；若当前请求更适合 `/lite:d2c`，则切换到该入口处理
- 在 `plan.md`、`tasks.md`、落盘确认和口头说明中，如需提到文件位置，只使用仓库相对路径，例如 `plans/2026-06-09-example/plan.md`；不要写入绝对路径

默认模式生成 `plan / tasks` 时，至少覆盖：

- 背景与目标
- 实现范围
- 系统依赖与影响面
- 待确认问题
- 风险点
- 待审核任务
- 长期知识沉淀判断

如果当前需求形成了可复用规则、模块边界、风险约束或项目级约定，需要：

- 明确说明“有可沉淀知识”
- 给出建议写入的主真源路径、文档标题或更新目标
- 说明沉淀依据

如果没有长期沉淀价值，也要明确写出“本次无建议沉淀的长期知识”。

未确认内容必须标记为：

- 待确认
- 待验证

不要把不明确的内容写成最终 task。

如果资料、数据结构或用户描述中存在明显不合理、缺失或相互冲突的地方，需要：

- 明确指出具体问题
- 说明为什么不合理，或会带来什么实现/体验风险
- 给出你认为更合理的处理方案或替代建议
- 必要时把该问题列入“待确认问题”或“风险点”

## 按需读取

- 需要判断当前应落在哪个状态时，读取 `references/plan/states.md`
- 需要处理外部资料访问时，先读取 `references/open/index.md`
- 只要外部资料来源命中 YApi、Figma、受限 Swagger/OpenAPI、原型系统或其他受限站点，就直接读取 `references/open/credentials.md`，不要等访问失败后再决定
- 需要判断设计稿类需求是“继续留在 `/lite:plan`”还是“切到 `/lite:d2c`”时，读取 `references/d2c/index.md`
- 需要提出澄清问题或判断歧义是否阻塞时，必须读取 `references/plan/clarification.md`
- 需要判断是否应沉淀长期知识时，读取 `references/knowledge/rules.md`
- 需要确定沉淀应写入哪个长期主真源，或 `docs/` 下哪个子目录时，读取 `references/shared/layout.md`
- 需要判断哪些信息可以进入目标项目、哪些只能作为执行约束时，读取 `references/shared/write-boundary.md`

## 与底层脚本的关系

AI 可在条件满足时调用 skill 内的 `scripts/` 执行器来完成：

- URL 采集
- context 生成
- plan / tasks 生成
- 生成后停在审查阶段

仅默认模式可调用会生成 `lite-spec` 的 `plan.md`、`tasks.md` 的脚本；直做模式和外部规划体系模式不要调用该生成器产出并行计划文件。

但对用户来说，`/lite:plan` 应始终表现为一个自然语言入口，而不是命令行工具包装。

### 脚本调用示例

脚本仅用于条件满足后的采集与草稿生成；若外部资料需要凭证，应先按 `/lite:open` 完成凭证检查。

Windows:

```powershell
skills/lite-spec/scripts/run-spec.ps1 -Repo . -Scope "新增订单导出"
```

macOS/Linux:

```bash
skills/lite-spec/scripts/run-spec.sh --repo . --scope "新增订单导出"
```

常用参数：

- `--api` / `-Api`：接口文档 URL
- `--prototype` / `-Prototype`：原型 URL
- `--figma` / `-Figma`：Figma URL；当前需要有效 `FIGMA_TOKEN`
- `--json` / `-Json`：直接传完整输入对象

其余参数与细节直接参考 `scripts/run-spec.ps1` 和 `scripts/run-spec.sh` 的参数定义。
