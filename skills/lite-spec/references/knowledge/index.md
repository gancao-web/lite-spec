# /lite:knowledge

用于判断当前需求、当前对话或用户指定范围内，是否存在应沉淀到长期主真源的知识。

它不是“只往 `docs/` 里补一份文档”的命令，而是“长期知识采集与主真源归位”入口：

- 先判断哪些知识值得长期保留。
- 再判断这些知识各自应该归属到 `README.md`、`AGENTS.md`、`docs/`、模块 `README.md`，还是继续留在代码附近。
- 如有必要，可以一次生成多份聚焦文档，而不是把所有信息压成一份总说明。

## 适用场景

- 用户明确要求“沉淀知识”、“整理经验到文档”、“看看这次需求有没有长期知识可收集”
- 用户希望基于当前对话、当前需求、当前项目或指定目录，识别长期有效的规则、边界和约定
- 用户希望把可复用业务规则、架构机制、模块边界或高风险改动约束沉淀到长期主真源
- 用户希望像“项目知识采集”那样，对仓库做一次全项目扫描，并把稳定知识分发到正确位置

## 主真源选择表

执行 `/lite:knowledge` 时，不要因为用户提到文档或 `docs/` 就默认把所有内容都写进 `docs/`。应先按信息类型选择主真源：

| 信息类型 | 默认主真源 |
| --- | --- |
| 项目入口、安装启动、常用命令、目录导航 | `README.md` |
| 项目特有 Agent 约束、高风险区域、验证要求 | `AGENTS.md` |
| 长期背景、架构机制、跨模块约定、运行手册、ADR | `docs/` 下合适文档 |
| 模块职责、关键流程、设计包袱、局部常见坑 | 对应模块 `README.md` |
| 代码已足够自解释的字段、类型、局部实现细节 | 继续留在代码、类型定义和注释附近 |

除非用户明确要求“只整理到 `docs/`”，否则应优先选择最合适的主真源，而不是强行集中到 `docs/`。

## 默认流程

1. 接收当前需求、当前对话或用户指定范围；若用户未指定范围、只输入 `/lite:knowledge`，则将范围默认扩展为整个项目
2. 提取需求范围、模块/服务、业务域、目录和已确认结论
3. 若是全项目知识采集，先扫现有长期文档、入口文档、目录结构和关键入口文件，建立项目级上下文：
   - `README.md`
   - `AGENTS.md`
   - `docs/`
   - 关键模块 `README.md`
4. 再扫项目骨架和关键入口，按“类别优先、文件名示例辅助”方式建立上下文：
   - 依赖与包管理入口：如 `package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`
   - 构建与运行入口：如 `Makefile`、`Dockerfile`、`tsconfig.*`、CI 配置
   - 服务或应用入口：如 `src/main.*`、`app/`、`cmd/`、`services/`、`server/`
   - 数据与迁移入口：如 `migrations/`、`sql/`、schema 定义、ORM 配置
   - 集成与接口入口：如路由、请求封装、消息队列、任务调度、CLI 命令、Webhook 或 worker 入口
5. 再从代码中补采那些已经稳定、可复用、但尚未被明确沉淀的事实、边界和约束，优先关注：
   - 运行时初始化顺序
   - 环境变量分层、配置来源与代理
   - 请求分流、上传、鉴权、日志链路
   - 路由树、命令入口、消息入口、任务入口或 worker 入口
   - 数据模型、迁移边界、缓存、队列、重试、幂等与回滚约束
   - 配置化页面能力、脚本参数、CLI 约定或服务编排前置
6. 最后选取高复杂度或高风险模块，补采模块级知识并写回模块 `README.md`：
   - 至少优先覆盖路由入口明确、业务体量较大、交互复杂、或容易踩坑的模块
   - 若模块已有 `README.md`，优先更新；没有时，仅在确有稳定内容时新建
7. 先把信息拆成三类：已验证事实、判断或设计原因、行动项；只有确实存在阻塞当前归位、且需要提醒用户后续核实的未验证项时，才额外单列“待验证问题”
8. 判断是否存在长期稳定、可复用、能约束后续实现的知识
9. 先按 `references/knowledge/rules.md` 判断是否值得沉淀；需要确定主真源或 `docs/` 子目录时，再读取 `references/shared/layout.md`
10. 若发现入口文档中混入了更适合独立维护的长期规则，应先执行信息归位：把规则迁移到更合适的长期主真源，再在入口文档中改为简短引用。
11. 直接写入沉淀建议对应的仓库相对目标路径；如适合，可同时补充信息归位表
12. 引导用户审核已落盘内容

不要在只看完 `README.md`、`AGENTS.md` 和少量配置后就结束 `/lite:knowledge`。全项目模式下，必须继续向代码入口和代表性模块下钻，直到能明确区分“项目级知识”和“模块级知识”。

## 默认产物形态

`/lite:knowledge` 的结果通常不是单个文件，而是一组按主题和层级拆开的文档：

- 项目入口索引：必要时更新 `docs/README.md`
- 项目级主题文档：例如 `docs/architecture/*.md`、`docs/standards/*.md`
- 模块级文档：例如 `src/pages/**/README.md`、`services/**/README.md`、`cmd/**/README.md`
- 入口摘要修正：必要时轻量更新 `README.md` 或 `AGENTS.md`，把过长规则改成摘要加指向

默认优先输出“少量、聚焦、按主题拆分”的文档，而不是：

- 只写一份泛化的项目结构说明
- 把运行时、请求、路由、权限、模块包袱混进同一份大杂烩文档
- 只更新 `docs/README.md` 却不补真正承载知识的主题文档

如果扫描后发现知识明显分成几束，应直接拆分为多份文档，例如：

- 运行时与环境
- 请求、接口与鉴权
- 路由、命令或任务入口
- 数据迁移、队列或调度约束
- 高复杂度模块 README

拆分标准应来自知识边界和后续查阅路径，而不是为了凑目录结构。

## 输出要求

至少覆盖：

- 本次分析范围
- 可沉淀知识判断
- 判断依据
- 信息分类结果：至少区分已验证事实、判断原因、行动项；只有存在未验证且值得提醒的问题时，才补充“待验证问题”
- 主真源归位结果：每条信息写到哪里、为什么
- 产物清单：新增、更新、保持不变的目标路径
- 若涉及信息归位，明确说明哪些内容应从 `README.md`、`AGENTS.md` 或其他入口文档迁出，并说明迁出后入口文档应保留什么级别的摘要
- 如需沉淀，直接生成文档内容或更新现有文档
- 如不需沉淀，明确说明原因
- 默认不要生成空的“待验证”章节；长期文档主体只承载已验证、可复用、可直接约束后续实现的知识

当 `/lite:knowledge` 进入全项目模式时，输出中还应显式回答：

- 哪些是项目级知识
- 哪些是模块级知识
- 为什么这些知识值得长期沉淀
- 为什么采用当前拆分方式，而不是单文档汇总

## 按需读取

- 判断文档是否属于长期知识时，读取 `references/knowledge/rules.md`
- 需要起草长期文档内容，尤其是 `docs/adr/`、`docs/runbooks/`、`docs/README.md` 时，读取 `references/shared/scaffolds.md`
- 需要判断主真源、长期文档分层、`docs/` 子目录是否应创建时，读取 `references/shared/layout.md`
- 需要判断哪些信息可以写入项目、哪些只能保留为本次执行约束时，读取 `references/shared/write-boundary.md`

## 硬性约束

- 只沉淀长期稳定、可复用、能约束后续实现的知识
- 必须先做“信息分类 + 主真源选择”
- 默认允许一次生成多份文档；只要信息边界不同，就不应压缩成一份总文档
- 若项目已有文档分层，优先沿用现有分层和命名；没有时，再按真实内容创建最少量的新文档
- 不把临时讨论、局部实现细节、未确认结论直接写入长期文档
- 未验证内容不能直接写成事实；如确有必要提及，只能在分析输出中标记为 `推断` 或 `待验证`，且不要写入长期文档主体
- 不要只沉淀“目录职责”和“验证要求”这类浅层信息；全项目模式下，还应优先沉淀运行机制、跨模块链路、权限关系和复杂模块包袱
- 所有文档内路径、建议落点、归位表目标位置和落盘确认，都只写仓库相对路径；禁止写入本机绝对路径
- 默认直接落文件后再提示用户审查，未获用户批准前不继续按这些沉淀结果改业务代码
