# lite-spec

通用项目的需求整理、任务拆解与知识沉淀工作流，适用于前端、后端、运维等工程化项目。

## 安装

```bash
npx skills add gancao-web/lite-spec
```
或
```bash
npx skills add https://github.com/gancao-web/lite-spec.git
```

## 安装本skill后，你可以跟AI说

- “这是设计稿和接口文档的链接，帮我实现 xx 页面”
- “这是设计稿，直接按现有项目风格把页面落出来”
- “这是原型图链接，先整理属于这个项目的需求，我审核后实施”
- “这个需求要改数据库表、接口返回和定时任务，先出一份实施计划”
- “这是运行手册和报警截图，先帮我整理排障范围、风险和执行步骤”
- “这个仓库要加一个脚本或 CLI，先帮我梳理影响范围、输入输出和验证方式”
- “这是工单、文档和几个链接，先帮我梳理实现范围、待确认项和验收点”
- “把这次讨论里值得长期保留的约束、规则和边界整理出来，沉淀到文档”
- “这个项目有哪些知识可以沉淀为文档”

它会
- 读取你发来的资料，以及当前项目上下文
- 按需采集常见在线资料源 (如 `axure`、`figma`、`yapi`、`swagger`、`openapi` 等，支持凭证访问)
- 整理符合当前项目的需求，识别待确认项、风险点和明显不合理之处
- 生成 `plan.md` / `tasks.md`，等你确认后才开始执行计划
- 按需把长期有效的规则沉淀为文档

## 为什么叫 lite

这个 skill 的出发点，就是想要一个比 `OpenSpec` 更轻的方案。

`lite` 代表的是：

- 轻计划：先把范围、风险、依赖、待确认项快速梳理清楚
- 快执行：产出够用的 `plan.md` / `tasks.md` 后，就可以进入实现或评审
- 可沉淀：不只为单次需求服务，也能在 plan 过程中顺手沉淀长期知识

它不是要替代完整的规格驱动体系，而是更适合日常高频迭代、需要快速推进但又不想失去知识沉淀的项目工作流。

## 和 `OpenSpec` 的区别

下面这个对比更偏向产品定位差异，用来说明 `lite-spec` 为什么存在：

| 对比项 | `OpenSpec` | `lite-spec` |
| --- | --- | --- |
| 核心思路 | 强调完整计划体系、规格驱动和流程约束 | 强调轻计划、快执行，先把事情推进起来 |
| 输出目标 | 更完整、更体系化的 spec / plan 产物 | 快速产出当前需求的 plan / task 产物 |
| 知识沉淀 | 以其规划流程中的产物沉淀为主 | 在 `plan` 过程中补充沉淀长期规则、约束和边界 |
| 定位特点 | 更适合围绕既有规划流程协作 | 更轻量，更适合日常高频需求推进 |
| 适合场景 | 统一计划体系、强流程协作的项目 | 快速推进、同时保留基本计划与知识沉淀的项目 |

- 若项目已经明确采用 `OpenSpec` 或其他稳定规划体系，那就继续用原有体系做 plan
- 当然`lite-spec`也支持跟它们一起工作，计划产物会优先遵循原体系的规则

## 和 AI工具 `plan` 模式的区别

下面这张表不是为了说明谁“更好”，而是说明两种方式在使用体验、产物形态和适用边界上的差异：

| 对比项 | AI工具`plan`模式 | `lite-spec` |
| --- | --- | --- |
| 主要形态 | 以对话中的计划输出为主 | 以对话 + 仓库内文档产物协同为主 |
| 呈现形式 | 信息停留在会话中，适合快速沟通 | 关键信息会落到文件里，团队成员更容易共享和追踪 |
| 沟通成本 | 需求较复杂时，反复在对话里补充、改写计划，往往更耗时间和 token | 先整理范围与风险，再沉淀成文档，通常能减少重复对话 |
| 文档产出 | 默认没有仓库内的长期文档产物 | 默认产出 `plan.md` / `tasks.md`，支持继续沉淀长期知识文档 |
| 资料访问 | 不直接处理需要登录凭证的外链资料采集 | 为需要登录凭证的资料访问补齐入口与规则沉淀 |
| 适合场景 | 已经很清楚需求，只想先在对话里快速列步骤 | 需求涉及多资料源、待确认项、风险梳理，且希望保留文档产物 |
| 局限性 | 更偏即时协作，不天然承担项目内知识沉淀职责 | 引入文档整理步骤，前置动作会比纯聊天计划稍多一些 |

如果只是想先快速列一个思路，AI工具的 `plan` 模式已经够用；而 `lite-spec` 更适合那些希望在推进需求的同时，把计划、任务和长期有效的约束一起沉淀下来的项目。

## 运行环境

- Node.js `>=18`

## 触发 Skill

除了自然语言触发 skill，你也可以通过命令显式触发

- 直接发送 `/lite:init`, 则是初始化项目的长期文档体系 (如需继续做长期知识扫描与沉淀，应再执行 `/lite:knowledge`)
- 直接发送 `/lite:knowledge`, 则是做全项目的知识沉淀
- 发送 `/lite:knowledge + 自然语言指定的范围`, 则是做当前对话或指定目录的知识沉淀
- 发送 `/lite:plan + 自然语言表述的需求` 为单次需求生成`plan.md`和`tasks.md` (待用户审核后，才执行代码)
- 发送 `/lite:d2c + 自然语言表述的需求`，按设计稿、原型图或截图直接落页面/组件
- 发送 `/lite:open + 链接` 为 AI 提供访问外部资料的能力，并沉淀访问规则与凭证约束 (如: 需要登录凭证的 `figma`、`yapi`、监控后台、在线文档)

## 输出产物

### 需求计划
`/lite:plan` 默认会把临时需求产物写到：

```text
<repo>/plans/YYYY-MM-DD-<slug>/
  plan.md
  tasks.md
```

其中：

- `plan.md`：实施计划
- `tasks.md`：待审核任务清单

## 长期文档

`/lite:knowledge` 不会默认把所有信息都写成长文档，只会把以下内容直接沉淀到合适文件：

- 长期稳定
- 可复用
- 能约束后续实现
