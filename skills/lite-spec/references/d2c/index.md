# /lite:d2c

负责把设计稿、原型图、截图或视觉稿落成现有项目中的页面或组件代码。默认路径是先补齐项目上下文与外部资料访问，再直接进入实现；只有当风险、范围或用户意图表明“不该直接写代码”时，才回切 `/lite:plan`。

## 适用场景

- 用户给出设计稿、原型图、截图或 Figma 链接，希望在现有项目中实现页面或组件
- 用户要求“按照设计稿完成 xx 页面”
- 用户希望已有页面按设计稿改版、补齐、重构或高还原实现
- 用户要求把视觉稿落成真实代码，而不是只出计划或描述
- 用户显式发送 `/lite:d2c`

## 默认目标

- 高还原设计稿的布局、层级、留白、字号、边框、圆角、按钮、图标、状态
- 优先复用项目已有组件、样式变量、资源体系和页面结构
- 输出符合当前仓库习惯的可维护代码，而不是临时拼装页面
- 避免为了追求局部像素一致而破坏项目整体一致性

## 核心原则

### 1. 先读仓库，再写页面

- 禁止只看设计稿直接开始写代码
- 实现前至少主动读取以下三类上下文：
  - 相邻或相似页面
  - 项目通用组件、布局容器、表单控件
  - 相关接口、类型、路由、状态管理或事件流
- 若页面属于已有模块，优先从该模块现有页面中学习结构和写法
- 若项目已有设计系统或组件库，默认优先复用，不重新发明基础组件

### 2. 优先复用，不默认新建

- 对页面壳、标题栏、表单项、按钮、弹层、列表、空态、开关、选择器、图标容器等，优先复用现有组件
- 不因设计稿的单次差异就重做基础组件
- 若现有组件与设计稿差异较小，优先通过组合、插槽、外层样式适配
- 只有在现有能力明显不足时，才新增局部实现或新组件

### 3. 先找相似页，再定实现方式

- 优先查看 2 个相似页面或相邻页面；若没有足够相似页，则改为查看最邻近页面、同模块其他页面、通用组件和全局规范，直到能形成足够的实现上下文。
- 优先学习以下内容：
  - 页面容器结构
  - 表单组织方式
  - 底部按钮区域
  - 滚动、吸底、安全区处理
  - 数据加载和提交方式
  - 成功返回、错误提示、事件刷新方式
- 若相似页之间写法不一致，优先选择离当前模块最近的一种

### 4. 设计资产必须校验，不要靠猜

- 不要假设仓库里已有某个同名图标或图片
- 设计稿中的图标、插画、按钮装饰、特殊分割线等视觉资产，必须先判断：
  - 项目中是否已有现成资源
  - 现有资源是否真正可显示
  - 现有资源的尺寸、方向、风格是否匹配设计稿
- 若现有资源不匹配，应优先从设计稿导出并落盘
- 图标资源默认优先使用 SVG
- 若 SVG 内含滤镜、模糊、阴影、遮罩、位图嵌入、复杂渐变或其他容易在目标端失真的效果，应优先改用 PNG 或让设计提供更适合交付的简化资源
- 当目标资源最终采用位图时，默认按目标端准备导出倍率：
  - 移动端项目默认优先使用 3x PNG
  - PC 端项目默认优先使用 2x PNG
  - 若项目自身已有不同资源倍率规范，优先遵循项目规范
- 新增资源应保存到项目可维护的位置，并遵循项目现有引用方式
- 不要把“缺资源”默认转嫁给用户；优先自行提取、导出、落盘
- 只有在无法稳定获取或设计稿本身缺失时，才请求用户补资产

### 5. 关键视觉点必须显式复核

实现完成后，至少复核以下高风险区域：

- 图标是否真实显示
- 按钮之间是否有设计稿中的明确间距
- 输入框占位、字号、颜色是否接近设计稿
- 圆角、边框、分割线、阴影是否方向正确
- 吸底按钮、底部安全区、键盘弹起后布局是否合理
- 左右留白、卡片间距、表单行高是否一致
- 开关、禁用态、空态、加载态是否符合设计稿或项目惯例

不要只凭“代码看起来像”就结束；关键局部应做视觉自检。

### 6. 优先项目一致性，再追求局部像素一致

- 若设计稿与项目通用规范存在轻微冲突，优先保持项目一致性
- 不要为了一个小图标、一个局部按钮而引入一整套不兼容写法
- 若设计要求会破坏已有交互体系，应采用“尽量还原 + 不破坏系统”的折中实现
- 对明显缺失的设计状态，可沿用项目现有交互习惯，不要随意发明

## 执行流程

1. 识别当前需求对应的模块、页面或组件，判断是新页面、旧页面改版，还是局部模块改造
2. 判断是否需要外部资料访问；若需要，先借用 `/lite:open`
3. 采集项目实现习惯，优先查看相邻页面、相似页面、复用组件、相关接口或类型
4. 明确复用策略，包括页面壳、组件、样式变量、图标和新增资源位置
5. 判断是否仍适合直接实现；若发现跨模块、高风险、高分叉或用户要求先规划，则回切 `/lite:plan`
6. 默认直接在目标代码中完成实现，并保持改动聚焦
7. 完成视觉与行为自检，确认关键间距、资源显示、提交流程、回显和刷新逻辑

## 默认直接实现

当同时满足以下条件时，默认直接写代码，不先出计划：

- 用户明确要求完成页面或组件
- 设计稿内容足够清晰
- 项目上下文可读
- 没有阻塞性权限问题
- 实现范围集中在一个页面或少量相关文件
- 不涉及明显的跨模块重构、架构调整或多方联动

## 回切 `/lite:plan`

当命中以下任一情况时，不应继续停留在 `/lite:d2c` 直做路径：

- 用户明确要求先出方案、先出计划、先别改代码
- 一个设计稿会影响多个模块、多个端或多个页面流转
- 涉及接口新增、数据结构调整、组件库改造或全局样式规范变更
- 设计稿与现有实现冲突明显，存在多种改法且代价不同
- 外部资料不可访问，关键设计信息缺失
- 存在高风险不确定项，不确认会导致大面积返工

## 资源策略

- 纯路径、小体积、无复杂滤镜的图标通常优先 SVG
- 含滤镜、模糊、发光、复杂阴影、位图混合等效果的图标，应改用 PNG
- 插画、照片、复杂纹理按需要使用 PNG 或 WebP
- 当资源采用 PNG 时，移动端默认优先 3x，PC 端默认优先 2x；若项目已有既定倍率规范，则跟随项目
- 资源命名、目录位置、引用方式遵循当前项目习惯
- 设计稿可稳定导出的资源，优先由 AI 自行处理
- 无法稳定导出时，再提示用户补充
- 禁止把“设计资产处理”一律甩给用户

## 禁止事项

- 禁止只看设计稿不看项目代码就开始实现
- 禁止忽略现有组件体系直接手写一套平行 UI
- 禁止假设图标文件一定存在
- 禁止发现图标不显示后仍继续交付而不说明
- 禁止把明显未核对的布局、间距、状态当作已完成
- 禁止在普通页面实现中无必要地引入新框架、新设计系统或大规模基础设施改造

## 输出要求

若任务保持在 `/lite:d2c` 直做路径：

- 直接完成代码修改
- 说明复用了哪些现有能力
- 说明是否新增了设计资源
- 说明已完成的校验，以及未能完成的校验

若任务回切 `/lite:plan`：

- 明确说明为什么当前不宜直接写代码
- 输出影响范围、风险点、待确认项
- 待用户确认后再进入实现
