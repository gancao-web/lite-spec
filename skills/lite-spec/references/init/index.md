# /lite:init

用于初始化本工作流的长期文档体系。

## 适用场景

- 项目开始建立长期文档体系
- 已有文档需要首次重整
- 需要梳理项目的长期主真源分布

## 默认行为

- 检查项目现状
- 直接写入初始化方案对应的目标文件
- 完成初始化后必须明确提示用户继续执行 `/lite:knowledge`

## 必读参考

执行 `/lite:init` 时，必须读取 `references/shared/layout.md`、`references/shared/scaffolds.md` 和 `references/shared/write-boundary.md`

## 工作流

1. 定位项目根目录；未指定路径时，默认使用当前工作目录。
2. 读取现有入口：`README.md`、`AGENTS.md`、`docs/`、重要模块 `README.md`；若项目已存在 `CLAUDE.md`，也一并读取。
3. 读取 `references/shared/layout.md`，判断长期文档层与临时计划层的推荐结构，以及哪些目录不应为完整性而创建。
4. 读取 `references/shared/scaffolds.md`，为需要起草的文件选择合适模板与最小内容。
5. 读取 `references/shared/write-boundary.md`，确认哪些信息可以写入项目、哪些只能作为本次执行约束。
6. 检查 git 状态，避免覆盖用户已有改动。
7. 若仓库已明确采用 `OpenSpec`、`Superpowers` 等现成规划框架，则初始化时不要再把 `plans/` 描述成默认适用的计划主真源；应明确说明长期文档层由 `lite-spec` 协助整理，但计划层沿用项目原有体系。
8. 形成初始化方案，并至少说明：
   - 建议创建或更新的文件
   - 每个文件的职责
   - 保持不创建的目录及原因
   - 长期文档层与临时计划层的分工
   - 写入边界检查结论
   - 如适合，可直接采用 `references/shared/scaffolds.md` 中的“初始化方案模板”
9. 直接生成或更新初始化目标文件，并保持内容可直接作为长期主真源使用。
10. 默认目标文件为：
   - `README.md`
   - `AGENTS.md`
   - `CLAUDE.md`
   - `docs/README.md`
   - 必要的模块 `README.md`
11. 所有写入文件内容、初始化方案、文件摘要、目标落点和落盘确认中的路径，都只使用仓库相对路径或仓库名；不要写入带盘符、主目录或用户名的绝对路径。
12. `plans/` 作为临时需求工作区，只在后续执行 `/lite:plan` 且项目未采用其他规划框架时按需创建；`/lite:init` 不默认预创建空目录。
13. 生成 `docs/README.md` 时，默认只写 `docs/` 目录本身的用途、目录约定和创建条件；不要重复根目录 `README.md` 的文档分工、安装说明或 `plans/` 工作区说明。
14. 若根目录 `README.md` 包含“目录说明”或目录树，且项目采用本工作流：
   - 若项目未采用其他规划框架，则列出 `plans/`，并用“按需创建”等短注释说明
   - 若项目已采用 `OpenSpec`、`Superpowers`，则在目录树或说明中明确“计划层沿用现有框架”，不要再把 `plans/` 写成默认主路径
15. 生成 `AGENTS.md` 时，默认只写 agent 执行规则、主真源约束和验证要求，不重复 `README.md` 中的项目介绍、安装说明和通用背景。
16. 默认确保根目录存在 `CLAUDE.md` 作为兼容入口：
   - 若项目不存在 `CLAUDE.md`，则创建最小内容，只引导查看 `AGENTS.md`
   - 若项目已存在 `CLAUDE.md`，则在文件顶部补充对 `AGENTS.md` 的引用，避免维护两套独立规则
17. 完成落盘后再告知：

- 已创建或更新的文件
- 长期文档与临时计划的主真源分布
- 用户接下来应如何审核这些入口产物并继续使用
- 最后明确提示用户下一步执行 `/lite:knowledge`，对当前仓库继续做长期知识扫描与沉淀

## 何时需要额外澄清

以下情况在输出初始化方案前，先停下澄清：

- 项目根目录不明确
- 目标文件已有明显人工改动，且本次初始化会影响核心内容
- 仓库已有另一套明确的文档结构，且迁移方向不清楚
