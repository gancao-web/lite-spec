# 长期知识沉淀规则

## 目标

- 统一判断什么内容应沉淀到长期主真源，什么内容只保留在代码或临时计划中。
- 降低“每个功能点都写说明书”带来的维护负担，同时保留对 AI 和新同学有价值的长期上下文。

## 主真源分层

优先做主真源选择，再决定是否写入 `docs/`。`/lite:knowledge` 表示这是长期知识采集入口，不代表所有产物都必须归入 `docs/`。

### 代码与模块内文档

- 单个功能点的局部字段、局部枚举、私有交互、接口映射细节，优先留在对应代码、模块内就近的类型/工具/配置文件，或模块目录 README 中。
- 能直接从代码稳定读出的事实，不必重复抄写到长期文档。

### 项目级入口与长期文档

- 项目入口、安装启动、常用命令、目录导航，优先归到 `README.md`。
- 项目特有 Agent 约束、高风险区域、验证要求，优先归到 `AGENTS.md`。
- 长期背景、架构机制、跨模块约定、运行手册、ADR，优先归到 `docs/` 下合适的主题文档。
- 模块职责、关键流程、设计包袱、局部常见坑，优先归到对应模块 `README.md`。

## 何时写入长期主真源

- 新增或确认了长期有效的项目级工程约定。
- 明确了跨模块或跨功能复用的业务规则。
- 形成了高风险目录的修改边界、验证要求或兼容性约束。
- 明确了会持续约束协作的 Git 提交规范、分支策略、评审约定或提交流程。
- 某个业务域复杂度明显上升，单看代码不容易快速建立正确上下文。
- 某项结论是 AI 或新同学高频会踩坑的隐性规则，且未来仍会持续生效。

## 何时不写入长期主真源

- 只是新增一个普通功能点或局部交互。
- 只是调整单个模块的局部字段、按钮或接口映射。
- 只是当前需求过程中的临时讨论、联调记录或未稳定结论。
- 只是代码里已经足够清晰的实现细节，没有额外的长期约束意义。

## 一般需求的默认处理方式

- 默认先更新代码，不为每次普通需求新增或修改单独补一份长期说明文档。
- 如果只是普通局部需求，优先留在当前需求的 `plans/` 工作区以及对应的 `plan.md / tasks.md` 中，不默认新增长期文档。
- 只有当需求背后沉淀出了可复用规则、模块边界或长期约束时，才回写到合适的长期主真源。

## 信息归位提示

- 若长期规则已经写在 `README.md`、`AGENTS.md` 或其他入口文档里，但内容明显超出“入口摘要”范围，应优先执行归位，而不是继续在原入口文档上堆内容。
- Git 提交规范、分支策略、评审约定、字段口径、目录边界这类规则，通常优先归位到 `docs/standards/`。
- 归位后，入口文档通常只保留一句简短提示和链接，帮助人和 AI 继续找到主真源。
- 若项目知识天然分成多束，例如运行时、请求与鉴权、路由与菜单、复杂模块包袱，应优先拆成多份聚焦文档，而不是压成一份总说明。
- 若知识明显属于模块上下文，应优先写模块 `README.md`，不要全部上收到根目录 `docs/`。

## 常见反模式

- 把 `AGENTS.md` 写成项目百科，混入大量背景介绍、命令说明或业务细节。
- 在 `AGENTS.md` 里重复 `README.md` 中的安装、启动和构建命令。
- 把较长的 Git 提交规范、分支策略或协作约定整段堆在根 `README.md`，却没有归位到 `docs/standards/`。
- 为了“结构完整”预先创建空的 `docs/` 子目录或其他占位目录。
- 把代码里已经清晰可见的字段列表、类型签名、接口参数细节整段抄进长期文档或模块 `README.md`。
- 把当前会话中的 system / developer 指令、全局规则、用户长期偏好当作项目事实直接写入文档。
- 把尚未确认的讨论结论、联调猜测或单次临时处理写成长期稳定规则。

## AI 协作建议

- 先读 `README.md`、`AGENTS.md`、`docs/` 与相关模块 `README.md`，获取规则和边界。
- 当用户只输入 `/lite:knowledge`、未指定范围时，默认把它当作一次全项目知识采集：先扫文档与入口，再扫目录结构和关键入口文件，最后从代码中补采稳定但未沉淀的项目知识。
- 全项目模式下，不要只停留在目录职责和验证要求；还应优先补采运行机制、请求与鉴权、路由与权限、环境与日志链路，以及高复杂度模块的长期包袱。
- 需要判断主真源或 `docs/` 子目录落点时，读取 `references/shared/layout.md`。
- 再读相关代码确认真实实现。
- 从代码补采时，优先关注启动入口、路由入口、配置、构建与发布脚本、关键领域模型、跨模块公共能力，以及那些已经长期成立但容易被新同学或 AI 忽略的隐性约束。
- 不要只读代码，也不要把所有实现细节都抄进文档。
- 只有当这些代码信息已经足够稳定，并且文档中尚未形成清晰主真源时，才补写到长期文档。
- 当代码与文档说明不一致时，以当前确认后的实现和规则为准，并及时修正文档。
