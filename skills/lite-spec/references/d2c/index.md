# /lite:d2c

负责把设计稿、原型图、截图或视觉稿落成现有项目中的页面或组件代码。补齐项目上下文和外部资料后默认直接实现；遇到高风险、大范围改动或用户要求先规划时，回切 `/lite:plan`。

## 适用场景

- 用户希望根据设计稿、原型图、截图或 Figma 链接实现页面或组件
- 用户希望按设计稿改版、补齐或重构已有页面
- 用户要求直接落成代码，而不是只出计划或描述
- 用户显式发送 `/lite:d2c`

## 默认目标

- 高还原设计稿的布局、层级、间距、样式和状态
- 优先复用项目已有组件、样式变量、资源体系和页面结构
- 输出符合仓库习惯的可维护代码
- 避免为了追求局部像素一致而破坏项目整体一致性

## 核心原则

### 1. 先读仓库，再写页面

- 实现前至少读取以下三类上下文：
  - 相邻或相似页面
  - 项目通用组件、布局容器、表单控件
  - 相关接口、类型、路由、状态管理或事件流
- 页面属于已有模块时，优先沿用该模块的结构和写法

### 2. 优先复用，不默认新建

- 页面壳、表单项、按钮、弹层、列表、状态组件等优先复用现有组件
- 单次或较小差异优先通过组合、插槽或外层样式适配，不重做基础组件
- 只有在现有能力明显不足时，才新增局部实现或新组件

### 3. 先找相似页，再定实现方式

- 优先查看 2 个相似或相邻页面；不足时补看同模块页面、通用组件和全局规范。
- 优先学习以下内容：
  - 页面容器结构
  - 表单组织方式
  - 底部按钮区域
  - 滚动、吸底、安全区处理
  - 数据加载和提交方式
  - 成功返回、错误提示、事件刷新方式
- 写法不一致时，优先采用当前模块的惯例

### 4. 设计资产必须校验，不要靠猜

- 不要假设仓库里已有某个同名图标或图片
- 对设计稿中的图标、插画、装饰等视觉资产，必须判断：
  - 项目中是否已有现成资源
  - 资源能否正常显示，尺寸、方向和风格是否匹配
- 若现有资源不匹配，应优先从设计稿导出并落盘
- 纯路径、无复杂效果的图标优先使用 SVG；含滤镜、模糊、阴影、遮罩、位图或复杂渐变时，优先使用 PNG 或简化资源
- 插画、照片和复杂纹理按需使用 PNG 或 WebP
- 当目标资源最终采用位图时，默认按目标端准备导出倍率：
  - 移动端项目默认优先使用 3x PNG
  - PC 端项目默认优先使用 2x PNG
  - 若项目自身已有不同资源倍率规范，优先遵循项目规范
- 新增资源应保存到可维护的位置，并遵循项目现有的命名和引用方式
- 优先自行提取、导出并落盘；只有无法稳定获取或设计稿本身缺失时，才请求用户补充

#### 设计资产导出与验收

- 优先导出设计稿定义尺寸的资源容器，保留原始留白和对齐基准
- 导出后核对 SVG 的 `width`、`height`、`viewBox` 或位图实际尺寸，确认比例、坐标系和目标层级正确
- 实际预览导出文件，不要只依据图层名称或导出结果判断资源有效
- 排查是否误带画布背景、超大矩形、渐变、无关分组、文字或祖先节点内容；应透明的区域不得出现不透明底色
- 作为 CSS Mask 使用的 SVG 必须是干净的单色轮廓；包含背景或多色内容时应改用其他渲染方式
- 将临时导出地址对应的文件下载并保存到项目，不要在代码中依赖可能失效的临时地址
- 在实际页面中验收资源的可见尺寸、留白、对齐、颜色、清晰度和相关状态
- 出现拉伸、裁切、背景污染或尺寸偏差时，应修正导出层级或资源文件，不要仅靠页面样式掩盖

### 5. 关键视觉点必须显式复核

实现后至少复核：

- 图标是否真实显示
- 按钮之间是否有设计稿中的明确间距
- 输入框占位、字号、颜色是否接近设计稿
- 圆角、边框、分割线和阴影是否正确
- 吸底按钮、底部安全区、键盘弹起后布局是否合理
- 左右留白、卡片间距、表单行高是否一致
- 开关、禁用态、空态、加载态是否符合设计稿或项目惯例

关键局部必须做视觉自检，不能只检查代码。

### 6. 优先项目一致性，再追求局部像素一致

- 若设计稿与项目通用规范存在轻微冲突，优先保持项目一致性
- 不为局部差异引入整套不兼容写法
- 若设计要求会破坏已有交互体系，应采用“尽量还原 + 不破坏系统”的折中实现
- 对明显缺失的设计状态，可沿用项目现有交互习惯，不要随意发明

## 执行流程

1. 定位模块、页面或组件，判断是新增、改版还是局部改造
2. 判断是否需要外部资料访问；若需要，先借用 `/lite:open`
3. 查看相邻或相似页面、复用组件、相关接口和类型，掌握项目惯例
4. 明确复用策略，包括页面壳、组件、样式变量、图标和新增资源位置
5. 判断是否仍适合直接实现；若发现跨模块、高风险、高分叉或用户要求先规划，则回切 `/lite:plan`
6. 默认直接在目标代码中完成实现，并保持改动聚焦
7. 完成视觉与行为自检，覆盖关键间距、资源显示、提交流程、回显和刷新逻辑

## 默认直接实现

当同时满足以下条件时，默认直接写代码，不先出计划：

- 用户明确要求完成页面或组件，且设计稿足够清晰
- 项目上下文可读，无阻塞性权限问题
- 范围集中在一个页面或少量相关文件
- 不涉及明显的跨模块重构、架构调整或多方联动

## 回切 `/lite:plan`

当命中以下任一情况时，不应继续停留在 `/lite:d2c` 直做路径：

- 用户明确要求先出方案、先出计划、先别改代码
- 设计稿影响多个模块、端或页面流转
- 涉及接口新增、数据结构调整、组件库改造或全局样式规范变更
- 设计稿与现有实现冲突明显，存在多种改法且代价不同
- 外部资料不可访问，关键设计信息缺失
- 存在可能导致大面积返工的高风险不确定项

## 禁止事项

- 禁止脱离项目代码，仅凭设计稿实现
- 禁止忽略现有组件体系，另写一套平行 UI
- 禁止假设图标存在，或在资源未正常显示时交付
- 禁止把未经核对的布局、间距和状态视为已完成
- 禁止为普通页面无必要地引入新框架、设计系统或大规模基础设施改造

## 输出要求

若任务保持在 `/lite:d2c` 直做路径：

- 直接完成代码修改
- 说明复用了哪些现有能力
- 说明是否新增了设计资源
- 说明已完成和未能完成的校验

若任务回切 `/lite:plan`：

- 明确说明为什么当前不宜直接写代码
- 输出影响范围、风险点、待确认项
- 待用户确认后再进入实现
